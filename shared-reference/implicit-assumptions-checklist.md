# 隐含约定 / 假设清单（req Gap Fill 必查框架）

**用途**：req 节点 Step 1.5 笔记 E + Step 3 Gap Fill 阶段，按 SRS 文本关键词触发分支，把"用户没说但下游必须对齐"的约定挖出来。**领域无关**——条目不写具体业务，只写"触发 → 应问 → 为什么"的结构。

**核心判别**：「这个假设错了，下游会怎么样？」若答案 = 测试都绿但实际不可用 / 反直觉 / 端到端断 / 数据错位 / 安全事故 / 在地化失败 → 必须在 req 阶段问清并写入 SRS。

**用法**：grep SRS 草稿 + 用户原话，命中关键词的分支必跑一次"应问清单"；用户已写明的跳过；未写明的进 Step 3 AskUserQuestion；用户答不上来的标 ASM-xxx 并记录失效风险。

---

## 分支 1：时间 / 时区 / 时序

**触发关键词**（任意命中即触发）：时间、时刻、时区、日期、过期、超时、调度、计时、延迟、deadline、cron、schedule、interval、timezone、UTC

**应问清单**：

- 显示时间用本地时区还是 UTC？以谁的本地为准（服务端 / 用户终端 / 数据所在地）？
- 跨时区跑批的"日"定义在哪个时区切割？夏令时切换日的处理？
- 闰秒 / 时钟回拨 / NTP 抖动是否影响业务？
- "立即"、"实时"、"立刻"的实际容忍延迟（毫秒？秒？分钟？）
- 定时任务的语义是"漂移"还是"对齐"（每小时整点 vs 每隔一小时）？
- 超时是单次调用还是整体预算？重试是否计入超时？

**反例**：以"时区不重要"为前提开发的跨境账单系统，上线后发现 UTC 日切与用户感知的"昨天"差 8 小时，账单按错日期归账。

---

## 分支 2：空间 / 坐标 / 方向 / 单位

**触发关键词**：坐标、位置、方向、移动、朝向、原点、轴、距离、面积、体积、几何、北/南/东/西、x/y/z、经纬度、像素、米、千克、温度、°C/°F、单位换算

**应问清单**：

- 坐标原点在哪？坐标轴方向（左手 / 右手系，y 轴向上还是向下）？
- 方向词（NORTH / UP / FORWARD）与显示坐标系是否一致？反直觉的组合是否需文档/UI 提示？
- 距离 / 面积 / 速度的基础单位是什么？输入 vs 显示 vs 存储是否统一？
- 经纬度的椭球体 / 投影坐标系？精度位数？
- 物理量是否含死区 / 量化步长 / 最小可测分辨率？
- 角度是度 / 弧度？正方向（顺时针 / 逆时针）？

**反例**：Web 应用屏幕 origin 在左上、y 轴向下，但业务约定"NORTH = 上"，导致用户按 N 后角色向 y 减少方向移动——视觉上"向上"但坐标值递减，反直觉。

---

## 分支 3：并发 / 会话 / 生命周期

**触发关键词**：用户、会话、登录、并发、同时、锁、事务、状态、生命周期、连接、超时、断线、重连、幂等、重复

**应问清单**：

- 同一用户多端同时操作如何裁决（最后写赢 / 先到先服务 / 拒绝并发）？
- 会话 / Token / 连接的生命周期、续期机制、过期处理？
- 操作是否需要幂等（重复提交是否合并）？幂等键是什么？
- 长事务中断如何回滚？补偿动作？
- 状态机的非法转移如何处理（静默忽略 / 报错 / 进入恢复模式）？
- 并发上限？超限时排队、限流、还是拒绝？

**反例**：忽略幂等性的支付接口，重试导致重复扣款；忽略多端会话裁决的协作文档，并发编辑相互覆盖。

---

## 分支 4：可观察输出 / 显示 / 反馈渠道

**触发关键词**：提示、通知、告警、显示、渲染、消息、弹窗、声音、震动、屏幕、终端、日志、回调、回报、通知方式

**应问清单**：

- 输出到哪些通道（终端 stdout/stderr / 屏幕 / 推送 / 日志 / Webhook / 消息总线 / 文件）？是否需多通道并行？
- 渲染层是否实际被业务逻辑驱动？业务事件 → 渲染事件之间是否有连接？（"代码里有告警逻辑但 UI 没接通"是常见失效模式）
- 反馈延迟容忍度？是否需进度提示？
- 不同环境（终端无图形界面 / 离线 / 静音）的降级方式？
- 多语言 / 屏幕阅读器 / 色弱适配？

**反例**：代码里完整实现「风险事件 → 触发告警 → 写入消息队列」三步，但 UI 没订阅这个队列、终端没消费这个 stdout，结果用户实操时风险事件发生而无任何可见反馈——"功能存在于代码但通道没接通"。

## 分支 5：错误码 / 异常语义 / 失败模式

**触发关键词**：错误、异常、失败、报错、拒绝、回滚、降级、超时、unavailable、retry、fallback

**应问清单**：

- 错误码命名空间（HTTP status / 内部 enum / 字符串），调用方如何区分可重试 vs 不可重试？
- 错误信息是否面向终端用户？需 i18n？需脱敏？
- 部分失败的语义（10 条数据 3 条失败 → 整体回滚 / 部分提交 / 标记跳过）？
- 上游不可用时降级到本地缓存 / 上次值 / 拒绝？
- 错误是否需上报观测系统？是否影响 SLA？

---

## 分支 6：数据格式 / 编码 / 命名习惯

**触发关键词**：字段名、JSON、XML、CSV、编码、UTF-8、GBK、序列化、命名、case、null、空值、空字符串、缺省

**应问清单**：

- 字段命名风格统一吗（camelCase / snake_case / kebab-case / 中文字段）？跨边界（API/DB/文件）是否需转换？
- null / undefined / 空字符串 / 缺省值 / 0 是否语义不同？
- 字符编码（输入 / 存储 / 输出三处统一吗）？BOM 处理？
- 时间戳序列化格式（ISO 8601 / Unix 秒 / 毫秒）？
- 文件编码 / 换行符（LF / CRLF）一致吗？

## 分支 7：安全 / 权限 / 数据可见性

**触发关键词**：权限、角色、登录、隐私、加密、敏感、token、密码、用户数据、可见性、跨租户

**应问清单**：

- 谁能看 / 改 / 删什么？权限模型（RBAC / ABAC / 字段级）？
- 敏感数据存储是否需加密？传输呢？日志中是否脱敏？
- 多租户隔离边界？误跨租户访问的检测？
- 审计日志的留痕粒度？
- 默认拒绝还是默认允许？

---

## 分支 8：可用性 / 性能 / 容量

**触发关键词**：性能、延迟、吞吐、QPS、扩展、规模、并发、数据量、存储、备份、可用性

**应问清单**：

- 预期数据规模（条 / 行 / GB / 时间维度的增长）？
- 关键路径的延迟 SLA？
- 峰值流量倍数？是否需自动扩容？
- 备份频率 / 灾难恢复 RPO/RTO？
- 单点故障容忍？

---

## 分支 9：兼容性 / 集成边界 / 协议

**触发关键词**：兼容、版本、API、协议、对接、上下游、库版本、平台、浏览器、操作系统、依赖

**应问清单**：

- 支持的运行时版本范围（语言运行时 / 操作系统 / 浏览器 / 库主版本）？
- 上下游契约稳定还是双方协调演进？破坏性变更如何通知？
- 旧版本数据 / 旧 schema 的迁移和回滚策略？
- 第三方依赖的可替换性？锁版本还是宽松版本？

---

## 分支 10：本地化 / 文化 / 法务

**触发关键词**：语言、翻译、本地化、i18n、l10n、文化、地域、法律、合规、GDPR、隐私法

**应问清单**：

- 支持哪些语言 / 地域？默认语言？回退策略？
- 文字方向（LTR / RTL）、复数规则、姓名顺序、地址格式？
- 数据存储是否受地域法律约束（数据本地化要求）？
- 隐私 / 同意 / 删除权（GDPR / CCPA / 各地数据法）？

## 通用反模式

| 合理化 | 正确动作 |
|---|---|
| "用户没说就按通用约定" | 通用约定是分支命中后才适用的默认值；先识别分支、再写明假设 ASM-xxx，让用户有机会推翻 |
| "这是实现细节不写需求" | 反直觉的约定（如 origin 位置、时区切割）是**外部可观察行为**，属需求；实现细节是"用什么算法 / 用什么库" |
| "只查 SRS 草稿不查用户原话" | 用户原话才是隐含约定的源头；草稿已经被翻译过、可能丢失关键词 |
| "命中多个分支只挑一个最重要的问" | 分支彼此独立，命中一个就跑一个；并问不耗预算 |

## 扩展机制

本清单是**框架**，分支条目可由团队 / 用户按领域扩展：

- 新分支：在末尾追加 `## 分支 N：<主题>` 节，按「触发关键词 / 应问清单 / 反例（可选）」结构填
- 新条目：在既有分支的"应问清单"末尾追加问句，保持 trigger → question 一对多关系
- 条目示例必须保持**领域无关 / 跨语言 / 跨交付形态**——若条目里出现具体业务名词（如某个产品名、某门具体语言的 API），抽象到更一般的描述
